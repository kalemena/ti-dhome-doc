= Core Services
:hardbreaks:

[IMPORTANT]
====
Core services are the base of the home automation project.
They are deployed as Docker containers on the home server.
====

Below is the list of core services to deploy, with the configuration used in this project.

.Services
* *MQTT broker* (Eclipse Mosquitto): central message bus used by all devices and services
* *Node-RED*: automation engine, ingesting and routing data between services
* *Victoria Metrics*: time-series database storing all metrics (Prometheus compatible)

A ready-to-deploy stack (Docker Compose + Makefile wrapping setup and management) is provided
in the `samples/core` folder of this repository.

== Architecture

All services expose their data over MQTT or HTTP and are linked together for example as follows:

* Teleinfo (Linky) -> Node-RED -> MQTT
* Zigbee energy meters -> Zigbee2MQTT -> MQTT
* OpenDTU (solar inverter) -> MQTT
* Node-RED -> Victoria Metrics (scraped / pushed)
* Grafana -> Victoria Metrics

== Deployment

The three services are deployed together as one stack with *Docker Compose*.
The project name is defined in `.env` (`COMPOSE_PROJECT_NAME=ti-dhome`) and prefixes all
auto-generated resources: containers (`ti-dhome-mqtt-1`), volumes (`ti-dhome_mosquitto-data`)
and the dedicated `ti-dhome` docker network. Services reach each other by service name
(`mqtt`, `nodered`, `victoriametrics`).

Persistent data is kept in Docker *named volumes*, one per service. This isolates the data of
each service and makes backup, restore and upgrade straightforward: upgrading an image or
recreating a container never destroys the data.

The stack management is delegated to a *Makefile* (`make up`, `make down`, `make setup`,
`make logs`, ...): see the `samples/core` README for the full command list.

== MQTT broker (Mosquitto)

The MQTT broker is the central message bus. Every device and service publishes to and
subscribes from topics on this broker. It is the single point the whole project talks through:
data producers (teleinfo, Zigbee meters, OpenDTU) publish, and consumers (Node-RED,
dashboards) subscribe.

.Two listeners
* Port 1883 for standard MQTT clients
* Port 9001 in *WebSocket* mode for browser-based clients and dashboards

The broker keeps persistence enabled: retained messages and client sessions survive restarts.

== Node-RED

Node-RED is the automation engine. It connects the data sources to the rest of the stack by
subscribing to MQTT, routing and transforming the data before sending it to Victoria Metrics.

.Deployed flows
* Teleinfo reader: consumes serial frames from Linky and publishes Power (W) and
  Energy (kWh) metrics to MQTT topics `teleinfo/#`
* Metric router: subscribes to `teleinfo/#`, `zigbee/#`, `opendtu/#` and forwards
  measurements to Victoria Metrics

.MQTT topics used
* `teleinfo/PAPP` - Instantaneous power (W)
* `teleinfo/BBRHCJB` - Blue HC counter (Wh)
* `teleinfo/BBRHPJB` - Blue HP counter (Wh)
* `teleinfo/BBRHCJW` - White HC counter (Wh)
* `teleinfo/BBRHPJW` - White HP counter (Wh)
* `teleinfo/BBRHCJR` - Red HC counter (Wh)
* `teleinfo/BBRHPJR` - Red HP counter (Wh)

== Victoria Metrics

Victoria Metrics is the time-series database used to store all metrics.
It is Prometheus compatible and used as the datasource for Grafana and the
*Mathematics* category analysis.

The instance is configured with a *retention period* (how long metrics are kept) and exposes:

* A UI (VMUI) for ad-hoc querying
* A Prometheus-compatible read API (`/api/v1/query`) used by Grafana
* A write API used by Node-RED and other scrapers/exporters

.Metrics written
.Example metrics
[source,text]
----
teleinfo_PAPP{location="main"}
teleinfo_BBRHPJB{location="main"}
zigbee_energy_b{location="Garage~PowerMeter"}
zigbee_energy_produced_b{location="Garage~PowerMeter"}
opendtu_YieldTotal{type="AC"}
sensors_*
----

== Security

Security is enforced by the following principles:

.Device authentication (MQTT)
The broker runs with *anonymous access disabled*. Every client (teleinfo, Zigbee, OpenDTU,
Node-RED) must authenticate with a user/password pair stored in the broker password file.
The password file is created once during setup and is *not* committed to version control.

.Listener separation
Standard MQTT and WebSocket listeners are both protected, so browser-based access requires
the same credentials as device access.

.Bound ports
Only the reachable endpoints are published to the host: MQTT (1883), MQTT WebSocket (9001),
Node-RED (1880), Victoria Metrics (8428). Services communicate internally through the
`ti-dhome` docker network and are not exposed beyond the host.

.Sensitive services
Node-RED and Victoria Metrics provide no built-in authentication. They are meant to stay on a
trusted network, and any access beyond the host should be put behind a reverse proxy with
authentication and TLS.

.Data isolation
Each service owns a dedicated Docker volume. Credentials, flows and metrics stay isolated
between services, which simplifies backup and limits the blast radius of a compromise.

.Granular access (optional)
For stricter setups, the broker supports ACL files to restrict which topics each user may
publish to or subscribe from, so a compromised device cannot read or forge other topics.
