= Mathematics - Energy Optimization Plan
:hardbreaks:

[IMPORTANT]
====
This file is a *work plan* for the optimizations described in the
`readme.adoc` of this category. It is not the implementation: each phase is
executed after this plan is reviewed. Scripts produced during implementation
are persisted here for *reproducibility* and are driven by handy `make`
commands.
====

== Objective

Answer, with real data held in VictoriaMetrics (1 year of measures), the
questions raised in `readme.adoc`:

* Is *Tempo* the good contract for our consumption? (contracts comparison)
* Where is energy consumed over the day/year, vs solar production?
* Where can consumption be shifted to solar or low-cost hours, and what is
  the saving under each contract?
* What if solar production is doubled or tripled? Where is the break-even
  point, and what battery size is optimal for each production level given
  our consumption profile?

== Constraints and strategy

*VictoriaMetrics caps queries at 30 000 000 samples per series.* A global
`increase(metric[365d])` therefore fails. The adopted strategy is:

* *Per-day sampling:* each counter is read once per day via an instant
  `max_over_time(metric[1d])` query (each query scans only one day).
* *Deltas in Python:* daily deltas of the cumulative counters give the daily
  increments (the pattern validated during the analysis session: 365 daily
  points from 2025-09-01 to 2026-09-01, all with data).
* *Hourly record:* hourly counter increments are exported once to CSV
  (8 760 points per metric) and become the *canonical record*; all
  downstream analyses (facts, profile, scenarios, batteries) reuse this
  file, including offline.
* *Hourly sum:* hour-of-day annual sums are rebuilt from
  `query_range(step=1h)` over the year + hourly deltas in Python, instead of
  the equivalent `sum_over_time(increase(metric[1h] offset h)[365d:1d])`.
* *Caching:* raw daily samples are cached to plain CSV so re-runs are fast
  and reproducible without re-hitting the database.

== Plan of phases

=== Phase 0 - Discovery probe

*Goal:* confirm the real metric names and label sets for all roles above.

*Actions:*
- Probe `/api/v1/series` for each candidate selector (opendtu, sensors_zigbee_*,
  sensors_teleinfo_*).
- Record exact selectors and units into `scripts/energy-config.yaml`.
- Confirm a full 365 days of data exist for each selector.
- *Data-quality check:* per day, compare Grid In daily increment with the sum
  of *available* Tempo counters (see note below), and classify days:
  * *inactive-color days:* White/Red counters silent while another color
    (Blue) increment is active -> expected, not a fault, because a Linky Tempo
    register only increments when its color/hours split is the active one;
  * *real gaps:* no tempo counter increments while Grid In > 0 -> flagged.
- *Hourly data-quality check* (`--checks hourly`, target `make hourly-check`):
  per-hour coverage for every counter (grid in/out, solar AC+DC, the six tempo
  counters), gap windows, solar daylight gaps vs expected night silence, and
  solar hourly increments beyond the physical 1 kW panel cap (~1 kWh/h).

[NOTE]
====
Result of the Phase 0 check (window 2025-09-01 -> 2026-09-01):

* Blue HP/HC: 0 silent days. White/Red silent only on spring/summer days
* where that color is inactive (76 days total), covered by the Blue counters.
* Yearly identity: Grid In = 3 345.9 kWh vs sum of Tempo counters = 3 406.2 kWh
* -> -1.8 % (Tempo over-measures, consistent +2..5 %/month, due to Wh-register
* rounding vs kWh metering). The 3 remaining days diverging >5 % (Mar/Apr 2026)
* are sub-kWh border effects.

*Solar consistency:* AC total = 1 013.6 kWh vs DC0 + DC1 = 1 013.6 kWh;
* one flat AC day (2026-05-24) excluded as known anomaly.

*Hourly data-quality check (`make hourly-check`, `--checks hourly`):* asserts
* hourly samples exist per metric counter and that solar cannot produce more
* than ~1 kWh/h (1 kW panels). Known anomalies are acknowledged in
* energy-config.yaml so the check passes while the report still lists them:

* - Grid In / Grid Out: 5 missing hours, single window 2025-10-12 05:00 -> 09:00
*   (zigbee meter outage) -> acknowledged PASS.
* - Solar (AC/DC0/DC1): 158 missing hours total; 72 are night silence (no sun,
*   expected), 62 daylight hours recorded as known anomalies, 24 flat-day hours
*   (2026-05-24, solar_flat_day) -> acknowledged PASS.
* - Solar over-max: 13 hourly AC increments beyond the 1.15 kWh/h cap (e.g.
*   4.42 kWh on 2026-03-17 15:00, 2.62 kWh on 2026-07-08 12:00); DC channels

* - Teleinfo: 273 stream-gap hours (all six Tempo counters silent together,
*   recurring daytime outages) + per-counter holes (blue_hc 33, white/red ~49-75).
*   Deliberately NOT acknowledged -> the hourly check FAILs until these are
*   reviewed / fixed, so the gaps stay visible.

=== Phase 2 - Hourly export (365-day record)

*File:* `01-hourly-export.py`, target `make export`.

*Goal:* build the *recording* used by every other phase and later mathematics:
one CSV row per hour of the year, with the hourly *increase* (Wh/kWh per
hour) of each cumulative counter.

*Computes for each hour of the 365-day window:*
- Solar Total (opendtu), Grid In and Grid Out (zigbee) hourly increments.
- Tempo HP/HC Blue, White, Red hourly increments (Wh -> kWh).
- Derived columns: auto-consumed solar (`solar - grid_out`) and home
  consumption (`grid_in + auto-consumed`), computed from the raw increments.

*Method:* `query_range(step=1h)` per metric over the year, then hourly
deltas computed in Python (scaling applied from `energy-config.yaml`). If a
full-year `query_range` hits the 30M-samples cap, fall back to per-hour
instant queries (as done in the analysis session).

*Output:* `scripts/output/hourly-energy.csv` (~8 760 rows) with columns
`utc_hour, solar_total_kwh, grid_in_kwh, grid_out_kwh, tempo_blue_hp_hc,
tempo_white_hp_hc, tempo_red_hp_hc, auto_consumed_kwh, home_consumption_kwh`.

[NOTE]
====
This file is the *single source of truth* for the maths in phases 3..7: they
read the CSV and work offline. Generation must stay deterministic from a full
cache.
====

*Solar catch-up correction (target `make correct-solar`).* The opendtu
`YieldTotal` counters freeze during daylight (repeating identical frames, i.e.
exact 0.000 increments) and then release the accumulated production in one
jump that exceeds the ~1 kW panel cap. The energy is real; only its
*placement* is wrong. The tool redistributes each release backward over the
preceding frozen/gap hours using a diurnal production template (hour-of-day
median from clean days), so every hour stays under the physical cap while the
counter total is preserved. Implemented in `01-data-quality.py` via
`--correct-solar PREFIX`; it reads VictoriaMetrics but *never writes* to it.

*Output:* `PREFIX-hourly.csv` (one row per hour per solar metric:
`metric, utc_hour, raw_kwh, corrected_kwh, confidence, flag`) and
`PREFIX-corrections.json` (per-metric summary + per-event log). Plain missing
hours that are *not* part of a release are intentionally left empty (listed in
`known_anomalies.solar_missing_hour`); their unallocated production is reported
per metric as `unallocated_kwh_in_missing_hours` rather than silently
interpolated.

=== Phase 3 - Yearly facts (readme "Setting the time facts")

*File:* `02-yearly-facts.py`, target `make facts`.

*Computes over the 1-year window (default 2025-09-01 to 2026-09-01):*
- Solar Total, Grid In, Grid Out (yearly increases).
- HP/HC Blue, White, Red yearly increases (Wh -> kWh).
- Auto-consumed Solar = Solar Total - Grid Out.
- Home Consumption = Grid In + Auto-consumed Solar.
- Identity check: Grid In vs sum(HP/HC Blue/White/Red), computed over the
  *available* counters per day (inactive White/Red days are expected and
  covered by the Blue counters, as established in Phase 0); reported
  PASS/FAIL against `identity_tolerance` (default 5 %).

*Source:* recomputes totals from `hourly-energy.csv` (offline) rather than
new DB queries.

*Output:* `scripts/output/facts.csv` + summary printed; identity check
reported as PASS/FAIL with delta.

=== Phase 4 - Contract comparison (readme "Is Tempo the good contract")

*File:* `03-contract-costs.py`, target `make contracts`.

*Computes the yearly cost under each contract and the ranking:*
* Base, Blue, Tempo, ZenFix, ZenFix-Tempo - exact formulas from `readme.adoc`
  (the sum of six teleinfo increases weighted by tariff).
* "Cost reduction" of Tempo vs Base (absolute and %).

*Source:* the six HP/HC tempo series of `hourly-energy.csv`.

*Output:* `scripts/output/contracts.json` + compact table (contract, cost, delta vs Tempo).

=== Phase 5 - Hourly solar / grid profile (readme "Can we optimize Solar")

*File:* `04-hourly-profile.py`, target `make hourly`.

*Computes for each hour 0..23, over the year:*
* Solar produced in that hour (opendtu).
* Grid In in that hour, split by High/Low cost periods (Tempo: HP and HC).
* Auto-consumed solar per hour (estimate).
* Surplus balance: Solar - Grid In per hour.
* Provide seasonal highlights by splitting into 4 seasons measure comparing metrics fro grid in/out and solr production

This supersedes functionally `mathematics-solar.py` (kept as legacy, see
below) and extends it from 3 metrics to the full
solar/teleinfo/zigbee set.

*Source:* `hourly-energy.csv`.

*Output:* `scripts/output/hourly-profile.csv` (24 lines) + optional Grafana-ready table.

=== Phase 6 - Shift scenarios (readme "Questions - predictions")

*File:* `05-shift-scenarios.py`, target `make scenarios`.

*Models "what if" moves with configurable assumptions (in energy-config.yaml):*
* Fraction of Tempo High-cost consumption shifted to Low-cost hours.
* Fraction of High-cost / all consumption shifted to solar hours (midday).
* Optionally, per-device consumers (Car, Water heater) if their metrics are
  provided in config (not required today).
* Recost each scenario under the 5 contracts.

*Source:* hourly consumption profile derived from `hourly-energy.csv`.

*Output:* `scripts/output/scenarios.json` + table of savings vs baseline Tempo.

=== Phase 7 - Solar scaling and battery sizing (new questions)

*File:* `06-solar-scenarios.py`, target `make solar-scenarios`.

*Models "what if we add solar" and "what if we add batteries" based on the
365-day hourly profiles (solar production and home consumption).*

.*What if we double / triple solar production?*
- Synthesize scaled solar profiles by multiplying the measured hourly solar
  by a factor `k in {1, 2, 3}` (assumption: new panels have the same shape;
  a different orientation is a configurable alternate profile).
- For each `k`, recompute per hour: auto-consumed solar, Grid Out (excess),
  Grid In (uncovered consumption), and the resulting yearly cost under each
  of the 5 contracts.
- Report break-even: which contract becomes the cheapest as `k` grows, and
  when Tempo stops being optimal.

.*What if we add batteries?*
- Hourly simulation for each `k in {1, 2, 3}` and a range of battery
  capacities (default `5, 10, 15, 20 kWh`, tunable in config), with battery
  model parameters in config: round-trip efficiency (default 90%), max
  charge/discharge power (kW), daily cycling.
- Battery charges from surplus solar (when production > consumption) and
  discharges to cover consumption (priority: cover grid draw; discharged at
  replacement of the relevant Tempo color / hours).
- For each `(k, capacity)` output: increase in auto-consumption %, reduction
  of Grid In (kWh and %), and yearly cost saving under each contract.

.*Optimal battery size:*
- Plot / table of marginal savings per added kWh of storage for each `k`
  (capacity vs yearly saving curve).
- "Optimal" = capacity where the marginal saving per kWh falls below a
  configurable threshold (default e.g. 30 cEUR/kWh-year), or where added
  storage no longer reduces Grid In.
- One recommended size is emitted per solar scale `k`.

*Output:* `scripts/output/solar-scenarios.json` (k x capacity grid of
savings) + `scripts/output/battery-sizing.csv` (marginal savings per
capacity and per k) + summary table.

== Acceptance criteria

* All 6 analysis phases run on the live VM via `make` with an empty cache.
* All 365 days (2025-09-01 -> 2026-09-01) yield data for every metric; any
  missing day is reported, not silently skipped.
* `hourly-energy.csv` contains 8 760 rows (+ header) with non-null values for
  every metric column.
* Contracts ranking reproduces the order/costs shown in `readme.adoc`
  (Base > ZenFix > ZenFix-Tempo > Blue > Tempo, with the associated costs).
* Solar scaling (x2/x3) and battery simulations are deterministic; battery
  sizing emits a recommended capacity per solar scale `k` where marginal
  savings drop below the configured threshold.
* Results are deterministic across runs (cache), and scripts work offline
  when the cache/hourly record is complete.
